# 17 — Cross-language conformance fixtures (Phase 2 of issue #48, "Parity is the risk")

**Depends on** task 14 (native core layout), task 15 (iOS/JS session logic), and task 16
(Android session logic) — this task only adds fixtures and fixture-driven tests on top of what
those three already shipped; it does not touch any of their production source.

## Goal

Issue #48's "Parity is the risk" paragraph: reconnect, registry, tool-invocation, bootstrap, and
SPKI-pinning logic now exists three times (TypeScript, Swift, Kotlin), ported from the same
original JS by three separate efforts. Nothing before this task forced the three to agree on the
same test vectors — each suite hand-wrote its own examples, so a future change to one
implementation's parsing/validation rules could drift from the other two without any test ever
failing. This task adds `packages/native/fixtures/`: language-neutral JSON vector tables, one per
protocol concern, that all three test suites load and assert identically.

## What's covered

Five fixture files, each with the exact vectors and rationale documented in
`packages/native/fixtures/README.md`:

- **`bootstrap-payloads.json`** — the v2 bootstrap binary layout (`docs/PROTOCOL.md` §2):
  well-formed IPv4/IPv6 payloads (including boundary session-id lengths and multi-byte UTF-8), and
  every documented rejection (wrong version byte, unknown family, truncated/oversized buffer,
  zero-length session id, invalid UTF-8 in it, port `0`). Positive vectors are generated by
  `@cordierite/shared`'s own `encodeBootstrap` (`scripts/generate-bootstrap-payloads.mjs`);
  negative vectors are hand-built from raw bytes, since `encodeBootstrap` refuses to produce most
  of them.
- **`bootstrap-links.json`** — the deep-link query-string layer around that payload: pin
  before/after the payload param, an unrelated param interspersed, a percent-encoded pin, a
  malformed pin (must be treated as absent, never forwarded), and the specific risk
  `docs/PROTOCOL.md` §2 calls out — a parser that slices from `cordierite=` to end-of-string
  instead of stopping at `&` would corrupt the payload with a trailing `&pin=...`.
- **`tool-descriptors.json`** — every rule in `docs/PROTOCOL.md` §5: the name pattern's bounds,
  description length bounds, schema fields that must be JSON objects, `annotations`'s closed set
  of boolean keys, and `timeout_ms`'s "positive integer or absent" rule (rejecting zero, negative,
  fractional, and string values), plus a `timeoutMs` camelCase key being a harmless no-op rather
  than a validated field.
- **`close-codes.json`** — the full `docs/PROTOCOL.md` §7 close-code table, tagged with whether
  each is terminal (1008, and only 1008, wholesale — never by matching the reason string), plus a
  few close events outside that table (1001, 1006, an unrecognized code, no code at all) to pin
  that "not 1008" always means "worth retrying."
- **`spki-pin.json`** — the one throwaway certificate + expected `sha256/...` pin that used to be
  duplicated as a string literal in `CordieriteConnectionManagerTests.swift` and
  `CordieriteSpkiPinTest.kt`; now sourced from one file both of those (and the new
  `packages/cordierite` test) read.

Consumers, one per language:

| Suite | File |
| --- | --- |
| vitest (`@cordierite/shared`) | `packages/shared/src/__tests__/fixtures-conformance.test.ts` |
| vitest (`@cordierite/cordierite` CLI, SPKI only) | `packages/cordierite/src/__tests__/spki-pin.test.ts` (extended) |
| XCTest (`CordieriteCore`) | `packages/native/ios/Tests/CordieriteCoreTests/FixturesConformanceTests.swift` |
| JUnit (`packages/native/android/core`) | `packages/native/android/core/src/test/java/com/callstackincubator/cordierite/FixturesConformanceTest.kt` |

Where a hand-written test already duplicated a vector now covered by a fixture (the SPKI
certificate/pin pair in the Swift and Kotlin suites), the duplicate assertion was removed in favor
of the fixture-driven one; the surrounding `PinningTrustManager`/`CordieriteConnectionManager`
behavior tests that also happen to use that certificate were left alone and now read the same
fixture file instead of their own copy of the literal.

Each test locates `packages/native/fixtures` relative to its own suite's natural anchor rather
than an environment variable or a copied resource: vitest via `import.meta.url`, XCTest via
`#filePath`, and the Gradle JUnit suite via `System.getProperty("user.dir")` (verified empirically
to be the `core` module directory under `:core:testDebugUnitTest`, with a walk-up fallback in case
a future Gradle/AGP version changes that). No `build.gradle` resource-directory wiring was needed
or added.

## What's deliberately not covered

- **Live socket behavior.** These fixtures are pure functions of a payload/URL/descriptor/code —
  encode/decode, validate, classify. The reconnect state machine, the actual TLS handshake, timing
  (backoff jitter, grace-window expiry), and anything that needs a real or fake transport are
  already covered by each suite's own integration tests (`CordieriteClientTests.swift`,
  `CordieriteClientTest.kt`, `client.test.ts`'s predecessors) and are out of scope here.
- **The wire message catalog** (`docs/PROTOCOL.md` §4 — `session_claim`, `tool_call`, etc.).
  Issue #48's JS deletion list removed `client/*.ts`'s message *construction*, but the guards
  themselves (`isSessionClaimMessage` and friends) still live only in `@cordierite/shared` — Swift
  and Kotlin talk to `CordieriteConnectionManager`, which the native cores don't re-validate
  independently of the daemon. There is no second implementation to diverge from yet, so no
  fixture was added for it; this would be a natural next fixture file if that changes.
- **The RN bridge's own wire-JSON parsing** (`packages/react-native/{ios,android}`,
  `parseToolDescriptorJson`/`RCTNativeCordierite.mm`). Out of this task's scope by the same
  boundary issue #48 itself draws: the three implementations under test are
  `packages/shared/src/domains/*.ts`, the Swift `Real/` sources, and
  `packages/native/android/core`'s Kotlin sources — not the thin bridges that vendor/wrap them.
  `tool-descriptors.json`'s Kotlin consumer therefore parses each vector's raw JSON into a typed
  `CordieriteToolDescriptor` itself (mirroring the wire-shape rules) before calling
  `validateCordieriteToolDescriptor`, rather than calling the bridge's own (out-of-scope,
  bridge-only) parsing function.

## Adding a vector

See `packages/native/fixtures/README.md`'s "Adding a vector" section. In short: edit the relevant
JSON file directly (or, for `bootstrap-payloads.json`, extend and rerun
`scripts/generate-bootstrap-payloads.mjs`), then run all three suites and confirm the new vector
passes in each. If it doesn't pass in all three, that is a real implementation divergence to fix
in whichever implementation disagrees with `docs/PROTOCOL.md`/`@cordierite/shared` — never a
reason to adjust the fixture to match the odd one out.

## Verification

- `pnpm build && pnpm test` — all packages build; `@cordierite/shared`'s
  `fixtures-conformance.test.ts` (87 assertions across the four JS-applicable fixture files) and
  `@cordierite/cordierite`'s extended `spki-pin.test.ts` both pass, alongside every pre-existing
  suite.
- `swift test` (repo root) — 113 tests, including the 6 new `FixturesConformanceTests` cases,
  all pass; `CordieriteConnectionManagerTests` (with the duplicate SPKI-pin literal test removed)
  still passes.
- `cd packages/native/android && ANDROID_HOME=$HOME/Library/Android/sdk ./gradlew
  :core:testDebugUnitTest` — 118 tests, including the 6 new `FixturesConformanceTest` cases, all
  pass; `CordieriteSpkiPinTest` (now reading the shared fixture instead of its own literal) still
  passes.

No divergence between the TypeScript, Swift, and Kotlin implementations was found while building
these fixtures — all three already agreed on every vector added here.
