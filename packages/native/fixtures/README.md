# Cross-language conformance fixtures

Issue #48, "Parity is the risk": the TypeScript (`@appduct/shared`, `@appduct/react-native`
where noted), Swift (`packages/native/ios`), and Kotlin (`packages/native/android/core`)
implementations of the same wire protocol (`docs/PROTOCOL.md`) must agree byte-for-byte and
rule-for-rule. Each file here is a language-neutral JSON vector table; each of the three test
suites loads every file and asserts every case against its own implementation, so a change that
makes one implementation drift from the others fails a test instead of shipping silently.

Consumers:

- `packages/shared/src/__tests__/fixtures-conformance.test.ts` (vitest)
- `packages/appduct/src/__tests__/spki-pin.test.ts` (vitest, `spki-pin.json` only)
- `packages/native/ios/Tests/AppductCoreTests/FixturesConformanceTests.swift` (XCTest)
- `packages/native/android/core/src/test/java/com/callstack/appduct/FixturesConformanceTest.kt`
  (JUnit)

## The rule

**A change to any one implementation's parsing/validation behavior must change a fixture file
here, and the updated fixture must still pass in all three suites.** If it doesn't pass in all
three, that's not a fixture bug to paper over — it's a real divergence between implementations,
and whichever implementation disagrees with `docs/PROTOCOL.md` / `@appduct/shared` (the
authoritative source per PROTOCOL.md's own header) is the one to fix, not the fixture.

## Files

### `bootstrap-payloads.json`

Array of `{ name, base64url, expected }`. `base64url` is a v2 bootstrap payload
(`docs/PROTOCOL.md` §2); `expected` is either the decoded fields
(`{ family, address, port, sessionId, tokenBase64url, expiresAt }`) or `null` for a payload every
implementation must reject.

Positive vectors are generated by `scripts/generate-bootstrap-payloads.mjs`, which calls
`@appduct/shared`'s own `encodeBootstrap` — so they're guaranteed well-formed by construction.
Negative vectors are hand-built from raw bytes in the same script (deliberately not going through
`encodeBootstrap`, which would refuse to produce most of them): wrong version byte (a v1 payload),
unknown family byte, a truncated buffer, an oversized buffer, a zero-length session id, invalid
UTF-8 in the session id, and port `0` — the exact rejection list `docs/PROTOCOL.md` §2 documents.
Includes both IPv4 and IPv6 positive vectors, a multi-byte-UTF-8 session id, and a 255-byte
(maximum-length) session id.

**To regenerate:** `pnpm build` (so `packages/shared/dist` is current), then
`node packages/native/fixtures/scripts/generate-bootstrap-payloads.mjs` from the repo root.

### `bootstrap-links.json`

Array of `{ name, url, expected: { payloadIndex, pin } }`. `url` is a full deep link
(`<scheme>:///?appduct=...&pin=...`, `docs/PROTOCOL.md` §2); `payloadIndex` is the index into
`bootstrap-payloads.json` whose `base64url` should equal the link's decoded `appduct` query
value; `pin` is the expected extracted `pin` query value, or `null` when absent or malformed.

Covers: no pin present, pin before/after the payload param (order independence), an unrelated
query param interspersed, a percent-encoded pin (a parser that doesn't URL-decode would fail to
match the pin's shape), a malformed pin that must be treated as absent rather than forwarded, and
— the case PROTOCOL.md §2 calls out explicitly — **a parser that slices from `appduct=` to the
end of the string instead of stopping at the next `&`** would swallow `&pin=...` into the decoded
blob and corrupt it; one vector's payload is deliberately the shortest fixture payload so that
kind of off-by-many-bytes corruption is unambiguous.

Hand-written, not generated: these are URL strings, not binary payloads, so there's nothing to
encode programmatically. When `bootstrap-payloads.json` is regenerated with different `base64url`
values, update the corresponding `appduct=` values here by hand and re-check `payloadIndex`.

### `tool-descriptors.json`

Array of `{ name, descriptor, valid }` covering every rule in `docs/PROTOCOL.md` §5
(`@appduct/shared`'s `isToolDescriptor`): the name pattern's bounds (empty, 65 chars, 64 chars,
invalid characters), the description length bounds (empty, 4096 chars, 4097 chars, missing,
non-string), schema fields that must be a JSON object if present (`input_schema`/`output_schema`),
`annotations` that must be a JSON object of only the three known boolean keys, and `timeout_ms`
that must be a positive integer if present (rejecting `0`, negative, fractional, and string
values) while a `timeoutMs` camelCase key is a harmless unknown extra, never a substitute, and
`group` that must be one or two `/`-separated name-pattern segments if present (rejecting an empty
string, empty segments such as `checkout/`, `/payment` and `a//b`, three segments, a 65-character
segment, other characters, a trailing newline, and non-string values including `null`). A
trailing-newline tool name is covered too: ICU's `$` matches before a final line terminator, so the
Swift port must check that its match spans the whole string. Also
covers a descriptor that is not a JSON object at all (a string, an array, `null`).

Hand-written directly as JSON (no generator needed — these are just JSON Schema-shaped documents,
not a binary format).

### `close-codes.json`

Array of `{ code, reason, terminal }`, one row per `docs/PROTOCOL.md` §7 close-code table entry,
plus a few close events *not* in that table (1001 `daemon_shutdown`, 1006 abnormal closure with no
reason, an unrecognized future code, and no code/reason at all) to pin the rule that **only 1008 is
ever terminal, matched wholesale by code, never by inspecting the reason string** — retrying a
1008 close can never succeed for any reason string, while every other code (1000, 1003, 1011,
1001, 1006, or anything unrecognized) is worth a reconnect attempt inside the grace window.

Hand-written directly as JSON, sourced from the table in `docs/PROTOCOL.md` §7.

### `spki-pin.json`

A single object: `{ description, certificateDerBase64, expectedPin }`. The certificate is the
same throwaway, self-signed EC (P-256) fixture certificate that was independently duplicated as a
string literal in `AppductConnectionManagerTests.swift` and `AppductSpkiPinTest.kt` before
this fixture existed — sourced from there, not reinvented. `expectedPin` is the `sha256/...` SPKI
pin `packages/appduct/src/spki-pin.ts`'s `createSpkiPin` produces for that certificate's public
key, which every implementation's SPKI-pinning code must reproduce byte-for-byte for a connection
to ever succeed.

No private key is included or was ever committed (this repo requires `git ls-files "*.pem"` to
stay empty) — the key was discarded after deriving `expectedPin` once.

## Adding a vector

1. Decide which file the new case belongs to (above).
2. For `bootstrap-payloads.json`: add a case to `scripts/generate-bootstrap-payloads.mjs` (either
   a `buildValid(...)` call for a well-formed payload, or a hand-built byte layout for a
   rejection case) and rerun it. For every other file: edit the JSON directly.
3. Run all three suites (`pnpm build && pnpm test`; `swift test` at the repo root; `cd
   packages/native/android && ANDROID_HOME=$HOME/Library/Android/sdk ./gradlew
   :core:testDebugUnitTest`) and confirm the new case passes in all three.
4. If it doesn't pass in all three, see "The rule" above — fix the implementation that disagrees
   with `docs/PROTOCOL.md`, not the fixture.
